# B200 optimization strategy - 2026-09-06

The first work should build a growing set of correct, independently benchmarked kernels, starting with fused reductions and elementwise primitives. SOL-ExecBench gives every kernel equal weight within its collection. A few individual #1 results will not produce a leading collection score.

## What creates score value

For workload latency `t`, stored scoring baseline `b`, and hardware bound `s`, the score is `(b-s)/(t+b-2*s)`. The documentation describes a [0,1] range, but the pinned `sol_score.py` returns the raw formula without a general clamp. The hosted backend is not public; no server-side clamp was verified. A correct baseline result receives 0.5; incorrect results receive zero. Kernel scores average workloads, and collection scores average kernels, with missing kernels contributing zero. [Scoring explanation](https://research.nvidia.com/benchmarks/sol-execbench/blog/introducing-sol-execbench).

The practical priority is `expected increase in kernel score / implementation-and-validation time`, divided by the collection size when comparing collection gains. Raw speedup and total runtime saved do not determine rank. Within a workload, score sensitivity to latency is `(b-s)/(t+b-2*s)^2`; use every stored workload row rather than scoring a geometric-mean latency.

Adding an L1 kernel at 0.7 raises the collection mean by 0.007447. Improving an existing L1 kernel from 0.7 to 0.8 raises it by only 0.001064. At the intended 1.0 SOL target, one L1 kernel contributes 1/94 = 0.010638 of the collection score. Planning with scores at or below that target, beating the present L1 leader requires at least 75 implemented kernels; at a 0.85 implemented-kernel mean it requires at least 88. Under the same planning assumption, 187 kernels are insufficient to exceed the unofficial combined score 0.795428. Do not treat these planning ceilings as verified server clamping behavior.

**Do not use live reference speedup as the score.** The current L1 reference implementation row scores 0.237027, while the distinct Scoring Baseline row is 0.5. The submission guide's quick-start claim that uploading the reference scores 0.5 conflicts with these current rows. Compute scores from each problem's stored baseline and SOL tables.

## Measurement and submission contract

[The official repository](https://github.com/NVIDIA/SOL-ExecBench) requires NVIDIA driver 580+, provides a Docker environment, and documents B200 SM clocks at 1500 MHz. It estimates ordinary latency variance around 5%, potentially 10% for many short kernel launches. Use the pinned evaluator, record driver/compiler/package versions, serialize GPU benchmarks, and keep clocks consistent. The Runpod host currently denies clock locking with `nvidia-smi` return code 4, including under sudo. Local measurements must therefore record unlocked clocks explicitly and cannot establish an official #1 result. A marginal local lead is not an established leaderboard win.

The [submission guide](https://research.nvidia.com/benchmarks/sol-execbench/blog/submission-guide) specifies 10 warmups, 50 timed iterations, three trials, cold L2, fresh cloned arguments, positional function arguments, and exact output shapes/dtypes. Its CUDA-event wording differs from pinned v1.1 code: `core/bench/timing.py` defaults to CUPTI activity timing and measures the span from the first user kernel's start to the last user kernel's end. That span excludes setup/cache work and CPU delay before the first kernel, but includes GPU idle gaps between a solution's kernels. It is not the sum of kernel durations. Standalone tuning must use that official CUPTI helper; CUDA-event intervals can include additional launch delay and give misleading rankings for microsecond kernels. Validate every official workload. No timing manipulation, hidden streams, background threads, lazy output objects, or substitution of constants for input-dependent work is permitted.

Single kernels accept Python, host C++ plus CUDA sources, or structured JSON. Collection archives currently accept per-kernel `submission.py` files only, under exact kernel directory names; missing directories score zero. Public submissions are leaderboard eligible. Standalone submissions 1–5 per UTC day have no reveal delay; later submissions add 10 minutes each up to 60 minutes, with at most five submissions in flight. Collections permit two submissions per collection per UTC day with a six-hour reveal delay. Use local correctness and tuning to conserve the immediate official results.
